## Scene 3 の画素を維持した最適化

`water_prepare(pose)` はページ2に背景と立体を保持します。ページ3から前の立体の外接矩形だけを復元し、統合したLMMV矩形をページ2に描きます。同じポーズは再利用します。`water_draw()` は縦に統合したHMMMと、左右端を1画素ずつ繰り返すLMMMを裏画面へ転送します。全面クリア・退避コピーは不要で、転送元は途中で変更しません。背景とテクスチャの読み込みでキャッシュを無効化します。

MESHは4,096バイト刻みを維持し、4092から外接矩形の4バイトを置きます。ラスタの元形状はビルド時のWavefront OBJ（既定 `assets/octahedron.obj`）です。WATERは512バイト刻みで、個数とsx/dx/幅/sy/高さの5バイトレコードです。IDENTITYは単一転送です。生成時に元のラスタと水面の行を照合します。`test-water-work.ps1 -Runtime <runtime>` は全ポーズ・再利用・Scene6からの再進入をVRAMで確認します。build.ps1の `-CStream` は診断用C処理を選びます。[段階別の測定とビルド・試験方法](../scene3-benchmark/OPTIMIZATION.ja.md)。


## ビルド

Python 3・Pillow と z88dk が必要です。通常のセットアップ・起動には不要です。このフォルダで実行します。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Z88dk "C:\z88dk"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Z88dk "C:\z88dk" -ProfileFilter '^external-0x88$'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Z88dk "C:\z88dk" -ProfileFilter '^internal-0x98$'
```

Linux / WSL でも同じプロファイル名を使います。

```bash
python3 build.py --z88dk ~/z88dk
python3 build.py --z88dk ~/z88dk --profile-filter '^external-0x88$'
python3 build.py --z88dk ~/z88dk --profile-filter '^internal-0x98$'
```

`external-0x88` は `VDP_BASE=0x88`、`internal-0x98` は既定の `0x98` でビルドします。フィルタを省略すると両方を作ります。`-Z88dk` には実際の配置先を指定します。`generate-fonts.py` と `generate-megarom.py` を毎回実行し、zsdcc で C をコンパイルします。固定領域が16 KiB以内、BSSがCF00未満、ROMが1 MiBであることを検査します。プロファイル名付き ROM は `V9968-TECH-DEMO-external-0x88.rom` と `V9968-TECH-DEMO-internal-0x98.rom` です。Windows / Linux の internal ビルドでは、既存の `test.ps1` / `launch.ps1` 用に `build/V9968-TECH-DEMO.rom`・`.map` と配布用 `V9968-TECH-DEMO.rom` も更新します。アセンブリで使う引数の warning 85 と PSG の最適化 warning 110 は残ります。

外付け HRA! V9968 カートリッジ（I/O base 0x88）には `V9968-TECH-DEMO-external-0x88.rom` を使用します。既存のopenMSX起動・テストスクリプトはcanonical internal ROMを使用し、外付けカートリッジを選択しません。コントリビューターが試験に使用した bitstream は HRA! commit `ceeecd7e3c2d25c20045f797617af0f70ca228c1` の [`fpga/V9968_Cartridge_TangNano20K/impl/pnr/tangnano20k_vdp_cartridge.fs`](https://github.com/hra1129/V9968_Cartridge/blob/ceeecd7e3c2d25c20045f797617af0f70ca228c1/fpga/V9968_Cartridge_TangNano20K/impl/pnr/tangnano20k_vdp_cartridge.fs) と確認されました。SHA-256 は `9ba903e7929bd9a6ef4b13fc6b1b49676015af05a52d97d8fa02c143643c6511` で、2026-09-18にそのcommitから取得したファイルとも一致しました。これはコントリビューターが使用した bitstreamの確認であり、今回再ビルドしたROMの実機試験結果ではありません。0.7.3 には両プロファイルの最終 ROM を同梱しています。

最終 0.7.3 external ROM の公開前の実機再確認は行っていません（リリース条件にはしていません）。公開 ROM での動作報告を歓迎します。報告時は ROM の SHA-256、機種、使用した bitstream のパス／ハッシュと RTL commit を添えてください。

## 素材と描画

`assets/chamber-source.png`・`assets/seabed-source.png` が編集用の元画像です。`python convert-assets.py` で16色画像を生成します。フォントは [MSX 8x8 font](third-party/fonts/README.ja.md) から変換し、ヘッダーの帯に合成します。`assets/PROMPT.txt` に画像生成条件を記録しています。

`MESH` の元形状は `generate-megarom.py --mesh-obj <file.obj>` で指定できます。既定は `assets/octahedron.obj`（ドーナツ形状）です。頂点 (`v`) と面 (`f`) のみを読み、`v`、`v/vt`、`v//vn`、`v/vt/vn` の面表記と負の頂点インデックスに対応します。テクスチャ・OBJ内の法線・マテリアル・グループ・スムージング指定は使わず、中心合わせ、自動スケール、フラットシェーディング、Zバッファをオフラインで行います。多角形面は扇状に三角形分割するため、凹多角形は事前に三角形化してください。

Scene 1・Scene 3・Scene 6 はすべて `BANK_MESH` を共有しているため、OBJを変更すると3シーンとも同じ形状へ変わります。Scene 1だけ八面体を残し、Scene 3/6だけ別形状にするには、別のメッシュ資産（または新しい実行時表現）が必要です。128×4096バイトの表をもう1個そのまま追加すると512 KiB増えるため、今回は1 MiB ROMと既存ランタイム形式を維持する方を優先しています。4096バイトの各レコードは、2バイトの個数と末尾4バイトのbboxを除くと、統合後の矩形を最大371個格納できます。生成器は全128姿勢でこの上限を検査し、超過したフレームを明示して停止します。複雑なモデルではOBJを簡略化・三角形化するか、`--mesh-radius` を小さくしてください。

SCREEN 5・256×192・16色で、拡張パレット、HS、LRMMを使用します。ページ0/1で描画と表示を切り替え、ページ3は背景と6本のヘッダー帯、ページ2はテクスチャまたは水の変形元です。

回転・投影、立体の走査線、床・回転パネル・水のパラメーターを事前計算します。固定コードは 4000–7FFF、バンク窓は 8000–BFFF で、7000H のレジスタで切り替える 64 バンクの ASCII16 です。バンク番号はすべて 256 未満のため、書き込みは標準 ASCII16 として成立し、ASCII16-X 対応ハードでも同じ動作になります。割り込みはバンクを変更しません。CF00 以降は検証情報、D000–D100 と D1D1–D1D3 は IM2 予約領域です。

stride で参照する資産は `bank-layout.h` に `FRAMES_<名前>` を出力します。実行時は `FRAMES_<名前>-1` でフレーム番号をマスクするため、生成側のフレーム数を変更しても次の資産を読み込むことはありません。生成スクリプトは各フレーム数が 256 以下の2のべき乗であることを検査します。

## ヘッダー

ヘッダーは全シーンとも画面に直接、ドロップシャドウ付きで描きます。影を文字の背後にあらかじめ合成した 186×9 の帯から、透明転送の LMMM を1回かけるだけです。以前はタイトル文字が背景画像へ焼き込まれており、毎フレーム先頭の背景転送と一緒に運ばれていました。そのため、画面の内容が背景画像と無関係な Scene 6 でも、ヘッダーを出すためだけに背景の帯を貼り直す必要がありました。現在はヘッダーの背後に何も貼り直す必要がなく、さらに背景の街並みテクスチャが細かい箇所でもタイトルが読めます。

影は色番号0ではなく1です。この VDP の透明転送は「色番号0を書かない」という意味であり、0 は黒です。つまり黒い字形は透明転送がちょうど捨てる対象で、黒は「書く」ことができず「落とす」しかありません。色番号1は31階調の (1,2,3) で、目には黒です。真の黒にするには、字形以外をすべて 15 にした反転マスクから不透明な LMMM の AND をかけ、字形の位置だけを落とす必要があります。これは正しく動き最初の版でもありましたが、文字列ごとに転送が1回増えます。影を帯へ合成し、さらにラベルとタイトルを同じ帯にまとめることで、ヘッダーの転送は4回から1回になりました。

6本の帯は、背景の上に空いている64行のうち54行を使います。LABELS はバンクだけ残しています。Scene 3 ベンチマークがそのバンクをフォントアトラスで上書きするためで、デモ側はもう転送しません。ヘッダーの背後を貼り直すシーンは Scene 3 も含めて無くなりました。Scene 3 のヘッダー帯は以前、周囲が波打つ中でそこだけ静止していました。これはタイトルが背景画像へ焼き込まれていた頃、貼り直さないとゴースト文字が波打ってしまうための措置でした。現在この帯も歪みの一部で、その上に文字が載ります。ヘッダーを従来どおり不透明転送1回だけにしたビルドとのシーン別実測では、合成帯方式によるフレームレート低下は最大 0.3% です。転送4回の版では最大 3% でした。

## Scene 6 のフィードバック

Scene 6 はヘッダーの出現を境に前半と後半へ分かれます。VRAM ページ2を借用します。本来はテクスチャと Scene 3 の水面キャプチャに使うページですが、入場時にクリアし、退場時に `textures_load()` を呼ぶため、追加のページは不要です。

時間の基準は自由走行する時計ではなく、シーンに入った時点の tick です。したがって手動で選んでも必ず冒頭から始まります。最初の180 tick が減衰トレイルで、ヘッダー帯・シーン名・上部の枠線を描きません。180 tick からヘッダーが出て以降は出たままとなり、4つのフィードバックフェーズが各180 tick で進みます。手動でシーンを保持している間はこの4フェーズが繰り返され、ヘッダーは表示されたままです。前半でヘッダーを隠すのは演出上の意図であり、退行ではありません。後半では他のシーンとまったく同じ HUD を描きます。

前半と後半はページ2を共有し、切り替え時にクリアしません。前半で溜まったトレイルがそのまま後半の最初の履歴フレームになるため、映像は途切れずに繋がります。

前半は色で減衰します。蓄積ページに対する全画面 LMMV（AND）1回で、全ピクセルの色番号からビットを落とします。前半はヘッダー帯・シーン名・上部の枠線を描かないため、ここではパレット16色すべてを自由に使えます。そこで「立っているビット数＝明るさ」と定義します。どのビットを落としても明るさがちょうど1段下がるため、元の色によらず減衰が均一になります。`palette_glow()` が前半のあいだだけこのグレースケールの popcount パレットを設定し、マスク `0x0e 0x0d 0x0b 0x07` は各1ビットずつ、4つ合わせて全ビットを落とします。したがって位相によらず1フレームあたりちょうど1段暗くなります。ビットを落とす操作はビット数を減らすことしかできないため、残像が明るくなることはありません。次の通常の `palette()` が16色すべてを書き直すので、後半へ漏れることはありません。

立体はランプの最上段である色番号15の一色で描き、15 → 14 → 12 → 8 → 0 と4段で均等に消えます。さらに減衰の前に、保持しているページを毎フレーム約5%拡大します。立体は毎フレームほぼ同じ画素を覆うため、その場に留まる残像は立体の下に隠れてしまうからです。拡大することで、消えていく複製が立体の下から外へ出ていきます。代償は1フレームあたりクリアと LRMM が各1回で、前半のフレームレートは実測 18.2 から 16.0 に下がりました。`stream_spans_glow()` は `stream_spans()` と同じパケット走査で、各 LMMV パケットの色バイトだけを転送時に15へ差し替えたものです。共有している MESH のスパンデータ自体は書き換えず、Scene 1 も同じ陰影付きOBJデータを読みます。陰影違いの複製を持てば ROM の半分を失うためです。色の差し替えは実際の欠陥も取り除いています。陰影のランプは8から始まりますが、8は二進 `1000` で立っているビットが最上位の1本だけです。4つのマスクのうち3つは8をそのまま残し、残る1つが背景へ落とすため、色番号8の画素は段階的に褪せることができません。周期のどこで書かれたかによって、最大3フレームのあいだ明るさを保ったままか、あるいは即座に消えるかのどちらかになります。読み込んだメッシュが色番号8を使う場合でも、この差し替えがあるため減衰には渡りません。

これが成立するのはパレット全体を使えるからであり、同時にこの演出を前半に限る理由でもあります。実測ではヘッダー帯の画素の86%が色番号0〜7を使っており、popcount パレットと正しい色のタイトルは16色の中で両立しません。ヘッダーが現れて以降の Scene 6 は、通常パレットと他のシーンと同一の HUD を共有します。

切り替え自体を綺麗に見せるために2点を対処しています。前半が引き渡すトレイルは popcount の色番号で書かれており、13・14・15 は通常パレットでは白・シアン・オレンジです。そのままでは後半がこの3色を何世代も再利用してしまいます。後半の最初のフレームでページ2にビット2を落とす AND を1回かけると、前半が生成しうるすべての色番号がメッシュの灰色帯（8〜11）か暗いランプ（0〜3）の内側に収まり、白・シアン・オレンジには落ちなくなります。これは値の範囲を制限する処理であって、明るさの順序を保つものではありません。popcount の順序と通常パレットの順序は別物だからです。もう1点、パレットの転送は1フレームに1回だけ、しかも `flip()` が tick を待った後に行い、垂直帰線期間に収めています。表示期間中に転送すると画面が裂けます。2回の転送の間に走査線が到達した範囲は別のパレットで描かれるため、前半にオレンジの帯が出ていました。ページ切り替えの後に行うことで、各フレームが必ず自分自身のパレットで表示されることも保証されます。

下部 HUD は前半も通常の色のままです。減衰は決まった巡回順で1フレームに1ビットずつ落とすため、15 から到達できるのは、落としたビットがその巡回順で連続している色番号だけです。すなわち 14・13・11・7、次に 12・9・3・6、次に 8・1・2・4、最後に 0 です。5 と 10 には到達しないので、下部の枠線と選択中インジケーターに空けておけます。15 は立体そのものなので、前半のインジケーターは 15 ではなく 10 で描いています。4 は到達しますが明るさ段1に位置し、そこに置く通常の色は置き換える灰色とほぼ同じ輝度です。

後半は代わりに幾何で減衰します。履歴ページを、クリア済みの裏ページへ HMMM（平行移動）または LRMM（拡大・回転）で転送し、その上に現フレームのメッシュを LMMV で描き、HMMM で次の履歴として取り込みます。平行移動は 256-|dx| × 192-|dy| しか書かないため、後ろ側の端に帯が残り、色0のクリアがそのまま見えます。拡大は異なります。ステップ251では転送先のどの画素も参照元がページ2の内側にあり、変換をオフラインで再現した結果は 49,152 画素すべてがエミュレーターの出力と一致しました。こちらでは履歴は侵食ではなく、画面外へ出ることで消えます。転送先のクリアは前半・後半とも必要です。LRMM を透明転送として発行しているためで、コマンドバイトの低位ニブルが論理演算にあたり、使用している値では参照元が色0の画素について転送先を書き換えません。クリアの目的は被覆ではありません。拡大では転送先のどの画素にも参照元がありますが、色0を読む画素は書かれないため、放置すると2フレーム前の裏ページの内容が残ります。不透明転送にすればクリアは不要になりますが、前半で 16.2 に対し 16.3 フレーム毎秒と測定の分解能の内側だったため、両半で同じ変換を使っています。CPU によるフレームバッファ処理、実行時の浮動小数点、実行時の sin/cos は使用しません。HUD は取り込みの後に描くのでループへ入りません。キャプチャテストはこれを直接検証しており、ヘッダー帯が画面上と同じ位置で履歴ページに写っていないかを調べています。

LRMM は転送先を1画素ずつ塗ります。現在の読み取り位置から参照元を読んで1画素を書き、その後で読み取り位置を進めます。vx/vy はその進み幅で、単位は画素の256分の1です。つまり 256 がちょうど参照元1画素ぶんにあたり、このとき等倍にコピーされます。251 だと毎回1画素より少し手前までしか進まず、転送先を塗り終えても参照元を読み切りません。その結果、参照元の狭い範囲が画面いっぱいに引き伸ばされます。これが拡大です。256 より大きくすれば縮小になります。参照開始位置は `panel_draw` と同じ「半幅・半高」の形で画面中心を履歴の中心に合わせます。ページ2は共有座標系の Y 512〜703 を占めます。

## R20 の bit5 を実行時に決める

R20 は bit0 が HS、bit4 が EPAL で、デモはどちらも必要とします。問題は bit5 で、これは V9968 の実装ごとに意味が異なります。固定している openMSX の派生版では拡張コマンドの有効化ビットであり、これを落とすと LRMM がまったく実行されません。Scene 6 のズームと回転の残像だけが消え、他は変わらないという形で現れます。一方、MSXimus が載せている HRA! 氏の6月版 FPGA マップでは、同じビットがフラットインタレースの選択で、これは不要です。そちらでは LRMM は bit5 なしで動きます。実機からの報告では、デモは 0x31 を 0x11 へ手で書き換えないと動かず、0x11 を書き拡張コマンドを使わないベンチマークはそのまま動きました。

1つの定数では両立しないため、`r20_select()` がハードウェアに問い合わせます。0x11 を書き、ページ0に 8×2 の矩形を1つ塗り、もう1つを消し、その間で等倍の LRMM を実行して転送先を読み返します。読み返しの前には、S#2 の CE が「立ってから落ちる」ことを待ちます。単に落ちていることを確認するだけでは不十分です。派生版は転送が即座に終わるため直後にポーリングしても成立しますが、実機の LRMM は時間がかかります。CE が立つ前に状態を読むとその読み出しは即座に戻り、転送前の転送先を読んで「動いていない」と判断し、bit5 がフラットインタレースを意味する環境でそれを立ててしまいます。立ち上がりを取り逃した場合は、すでに転送が完了していたことを意味するだけなので無害です。転送が起きていれば拡張コマンドは既に有効なのでビットは立てず、起きていなければそのビットが有効化の役割なので 0x31 を書きます。直後にページ0全体をクリアするため2つの矩形は残りません。選んだ値は 0xcf09 に記録します。

派生版での実測では、読み返し値は 0x11 のとき 0x00、0x31 のとき 0xff でした。常に一方へ倒れるのではなく、両方向に判定が効いています。派生版では 0x31 が選ばれ、前半と LRMM を使う両フェーズを含めて、0x31 を無条件に書いていたビルドと画素単位で一致します。実機側の分岐は当方では実行できていません。

## マッパーの選択と 1 MiB を超える場合

`bank_select()` はバンク番号の下位8ビットをデータとして、上位ビットを A8–A11 に載せて書き込みます。これは ASCII16-X の符号化そのものです。64 バンクでは上位ビットが常に 0 になるため、書き込み先は必ず 7000H、データはバンク番号となり、標準 ASCII16 として成立します。**1つの実装が両方のマッパーを同時に満たしており、この ROM は ASCII16-X 対応ハードでもそのまま動作します。**

ASCII16 を宣言しているのは、対応環境が圧倒的に広く、このデモが拡張機能を必要としないためです。ただし現時点で実際に動かせるのはエミュレーター利用者です。V9968 は実機としては HRA! 氏の FPGA カートリッジしか存在しないため、マッパーの対応範囲は今すぐ効く利点ではなく、将来のための余地と位置づけています。

8ビットのレジスタにより ASCII16 は 256 バンク＝4 MiB が上限です。これを超える場合は次の手順です。

1. `generate-megarom.py` の `ROM_BANKS` を増やす。`MAPPER` が `ASCII16` のまま 256 を超えると生成が停止し、エラーメッセージが切り替え先を示します。
2. 同ファイルの `MAPPER` を `ASCII16-X` にする。
3. `launch.ps1`・`test.ps1`・`test-water.ps1` の `-romtype` を変更する。
4. `launch.ps1` と `tests/validate-public.ps1` の 1,048,576 バイト検査、`config/versions.json` の `demo` 項目を更新する。

**`mapper.c`・`mapper.h` および描画コードの変更は不要です。** なお ASCII16-X は 8000H–BFFFH のデータ窓内にもレジスタのミラーを持ちます。このデモは当該領域を読むだけなので影響しませんが、将来この窓へ書き込むコードを追加する場合は注意が必要です。

`platform.c` は独立した実装です。カートリッジ起動時にページ0のBIOSを呼び、turbo Rでのみ CHGCPU(0180h)、A=81h によりR800 ROMモードを選びます。キーボードはPPIのAAh/A9hを使用し、選択レジスターを読み取り後に復元します。ライブラリ由来のコードは含みません。

C-BIOSは最後のパスを `cbios` に変更します。`test.ps1` は6シーン、キー1・3・0・W・Esc、VDPエラー、バンク、背景、全シーンのヘッダーの画素単位一致、Scene 3 のヘッダー行が水面とともに動くこと、R20 の判定がこの派生版に必要な値を選んだことを確認します。`test-water.ps1` は無変形と変形時の水処理を独立した参照値と比較します。所有BIOSを含む `test-output/` は公開しません。通常起動の専用データは `runtime/<mode>/user-tech-demo/<SHA-256先頭12文字>/` に保存します。

[開発版の検証結果（JSON）](verification.json) を参照してください。現在の八面体の試験と過去の記録はROMハッシュで区別しています。任意モデルの試験はOBJ検証記録を参照してください。実機、別エミュレーター、4 MiB超、18分超の連続再生、音質は未検証です。16ビット時計は約18分で周回します。CPUやフォントの識別成功は、すべての機能の動作保証ではありません。

W キーはキーマトリクスの行5・ビット4です。テストでは Y が切り替えに反応しないこと、W の長押しで再切り替えされないこと、離して押し直すと戻ることを確認します。描画完了時の VRAM も比較し、OFF では変形前の作業画面と一致、ON では変形して異なることを検証します。キー入力はエミュレーターへの注入で、物理キーボードによる操作確認とは区別しています。

## C実装とアセンブラ実装の比較

`V9968_SCENE3_C_STREAM` をビルド時に定義すると、`v9968.c` のメッシュ・残光・水面の転送処理をC実装に切り替えます。`build.ps1 -CStream` がこの定義を渡します。C実装を `#if 0` で無効化せず、対応するアセンブラの直前に置き、両方をコンパイル・実行できる状態で維持します。

| 処理 | C実装とアセンブラの対応 |
| --- | --- |
| CE待機 | `wait_cmd()` ↔ `stream_wait()`。最大65,535回のポーリングと同じ異常停止処理 |
| メッシュ | `stream_mesh_page()` の2実装。11バイトのR36〜R46パケットを送り、3番の描画先ページだけ置換 |
| 残光 | `stream_spans_glow()` の2実装。描画先ページと8番の色を15へ置換し、幅・高さ・コマンドを維持 |
| 水面 | Cの `water_draw()` ↔ `stream_water_runs()`。帯の主転送と端の1画素反復を同じ順序で出力 |

同じ入力から同じ画素・ページ・コマンド効果を得ることを比較します。実行時間、命令数、割り込みが入る位置は同一ではありません。時間でポーズが進むため、連続再生の各フレームが一致するとは限りません。ポーリング回数は同じでも、タイムアウトまでの実時間は異なります。

割り込み入口のレジスター保存と `RETI`、`DI/EI`、IM2設定、原子的な16ビット時計読み出し、BIOSのレジスター引数は専用処理を維持します。単純なCへの置換は割り込みABIやタイミングを壊すため、C表記の処理概要をコメントで対応付けています。バンク選択にも等価なCのメモリ書込みを併記しています。今回の範囲では、ファイル分割による配置・ABIの変化を避け、同じ翻訳単位内で隣接させました。

リポジトリ直下で実行します。`<z88dk>` と `<runtime>` は実際のフォルダへ置換してください。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File demos/v9968-tech-demo/build.ps1 -Z88dk "<z88dk>" -CStream
powershell.exe -NoProfile -ExecutionPolicy Bypass -File demos/v9968-tech-demo/test.ps1 -Runtime "<runtime>" -CStream
powershell.exe -NoProfile -ExecutionPolicy Bypass -File demos/v9968-tech-demo/test-water.ps1 -Runtime "<runtime>" -CStream
powershell.exe -NoProfile -ExecutionPolicy Bypass -File demos/v9968-tech-demo/test-water-work.ps1 -Runtime "<runtime>" -CStream
powershell.exe -NoProfile -ExecutionPolicy Bypass -File demos/v9968-tech-demo/test-glow-stream.ps1 -Runtime "<runtime>" -CStream
```

C版は `build-c/`、通常版は `build/` に生成します。C版は配布ROMや既存の測定記録を上書きしません。通常版の検証では `-CStream` を外します。残光試験はシーンの時計を固定して全128形状と描画先ページ0/1を画素比較するもので、性能測定ではありません。両CPU・両実装の検証結果は [C/ASM比較結果（JSON）](stream-verification.json) に記録します。

[OBJの検証結果](obj-verification.json)。C/ASM比較の旧記録は0.7.1のROMに対する結果です。今回のOBJ検証は既定ASMビルドで実施しています。
