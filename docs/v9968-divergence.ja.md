# V9968 実装間の食い違い

合意された V9968 は存在しません。量産されなかったため、どの実装も仕様の解釈であり、少なくとも1つのレジスタビットが実装によって別の意味を持っています。これは資料を読んで見つかったのではありません。エミュレーター向けに書いたデモが、1バイト書き換えるまで FPGA 実機で動かなかったことから判明しました。

このページは、実装が分かれていると分かっている箇所と、分かれている疑いのある箇所の一覧です。そして各実装が実際に何をしたかの記録です。どちらが正しいかを裁定するものではなく、観測の記録であることを意図しています。

## 列を追加するには

お手元の機械で `probe/PROBE.rom` を実行してください。テストごとに1行ずつ表示して停止します。表示された行をそのまま、実行環境と併せてご報告ください。

起動直後のカートリッジとして使用してください。作業用 VRAM と VDP レジスタを書き換え、最後に BIOS INITXT で新しいテキスト画面を初期化します。実行中のアプリケーションの状態は保存しません。指定するアドレスは 0x8000 以上ですが、未知のアドレスデコードでは下位領域へ折り返す可能性があります。ディスクへの書き込みやフラッシュの書き換えは行いません。FPGA 実機での実行は未確認で、表示が完了しない場合はリセットしてください。現在は98h/99hを使う内蔵VDP用であり、88h/89hの外付けカートリッジ用ではありません。

```
V9968 / C ROM TEST
VDP ID=3
V9968 IDENTIFIED
R20B5  off=0 on=1
R20SEL value=31
LRMMOP timp=ff imp=00
LRMMST d0=1 d1=2
CE     rise=0 fall=15
CESEEN value=1
VRAM   a1 a2 a3 a4
REPORT THESE LINES
```

## 各行が何を調べているか

### `VDP ID=` — 識別シーケンス

HRA! さんの `init_vdp()` と同じ手順で VDP 識別値を読みます。V9968 なら 3 を返します。それ以外の場合、以降のテストは実行していません。

### `R20B5` — R20 の bit5 の意味

**これが確認済みの食い違いであり、このページが存在する理由です。**

bit5 を立てずに R20 を書き、小さな矩形2つの間で等倍 LRMM を1回実行し、転送先を読み返します。次に bit5 を立てて同じことをします。`off=1` は、そのビットが無くても拡張コマンドが動くことを意味します。

固定版の派生エミュレーターでは bit5 が拡張コマンドの有効化ビットで、落とすと LRMM は何もしません。HRA! さんが公開している FPGA のマップでは、同じビットがフラットインタレースの選択で、bit5 なしで LRMM が動きます。1つの定数では両立しないため、デモは起動時にこれと同じ実験を実行して値を決めています。

エミュレーター向けに0x31を書くとFPGAではフラットインタレースを選ぶ可能性があり、FPGA向けに0x11を書くと固定版エミュレーターではLRMMが無効になります。プローブは両方を調べ、0x11で転送できればそちらを優先し、そうでなければ転送できた0x31を使います。R20SELが選択結果です。どちらでも転送できない場合はLRMMOP/LRMMSTを省略し、変化しなかった転送先から演算の意味を推論しません。

### `LRMMOP` — LRMM に適用されるロジカルオペレーション

コマンドバイトの下位4ビットがロジカルオペレーションです。演算8は透明版で、転送元の画素が色0の位置では転送先を書き換えてはなりません。演算0は上書きしなければなりません。

転送元を色0、転送先を色15で埋め、LRMM を2回実行します。`timp=ff` は透明転送が転送先に触れなかったこと、`imp=00` は不透明転送が上書きしたことを意味します。これ以外の組み合わせは、演算の欄が LRMM に同じようには適用されていないことを示します。

これは見た目以上に重要です。透明転送は転送先の全画素を書くわけではないため、画面を覆う目的で使うコードは事前に転送先をクリアする必要があります。ここを取り違えると、エラーではなく**古い内容が残る**という形で現れます。

### `LRMMST` — 参照元の読み取り開始位置

LRMM は転送先を1画素ずつ塗りながら、参照元の読み取り位置を進めます。画素を書く前に進めるのか後に進めるのかで、結果全体が参照元1画素ぶんずれます。

1・2・3…と並ぶ行を等倍・不透明でコピーします。転送先を15で初期化し、先頭2画素を同じ1バイトから読みます。`d0=1 d1=2` は読み取り後の加算、`d0=2 d1=3` は読み取り前の加算を支持します。それ以外の組は判定不能で、直ちに別の加算規則とは結論しません。

### `CE` — コマンドエンジンの所要時間

`rise` はエンジンがビジーを報告するまでに行った状態読み出しの回数、`fall` はビジーであり続けた読み出しの回数です。コマンドは1ページ全体の塗り潰しなので、実チップには相応の仕事があります。

これはソフトウェアのポーリング回数であり、経過時間やVDPの速度倍率ではありません。CPUモード・クロック・ROMハッシュ・エミュレーター／FPGAのリビジョン・R20SELを一緒に記録してください。コマンドはSCREEN 5の256×192 HMMVで、表示と割り込みを停止して測ります。CESEEN=0は20,000回以内にビジーを観測できなかった意味で、観測前の完了と未開始を区別できません。ビジーが60,000回を超えれば測定値ではなくエラーです。他のコマンドは開始猶予1,024回、ビジー待ち20,000回です。これらは無限ループを防ぐ上限であり、実機のタイミングに基づく保証値ではありません。PROBE ERROR code=1はビジー待ちの時間切れ、code=2は転送元・転送先の準備失敗です。中断後は途中の結果を破棄し、テキスト画面を初期化します。

機械間の時間比較を行うなら、将来は複数コマンドを長い区間で繰り返し、共通仕様のタイマーやVBlank回数で測る方法が適しています。非常に短いCEパルスにはサイクル数を確定したループや外部測定が必要です。このプローブは実機のタイミングを保証しません。

### `VRAM` — 実際にアドレスできる容量

0x8000、0x10000、0x18000、0x1c000（R14=2,4,6,7、オフセット0）へマーカーを書き、保存していたバイトを戻します。R14はSCREEN 5のページではなく16 KiBブロックを選び、最後の間隔は16 KiBです。異なるマーカーが示すのは、このモードでこの4アドレスが別名でないことだけです。128 KiB全域や256 KiB容量の証明ではありません。重複は別名の可能性を示しますが、書き込み失敗や読み取りタイミングの問題も除外する必要があります。

## 未着手

変わりうると疑っていますが、まだ実験を書いていない項目です。カートリッジに次に足すとすればここです。

- **LRMM のクリッピング。** 回転・拡大した読み出しが参照元のクリップ枠の外に落ちたとき、転送先の画素は放置されるのか、色0で書かれるのか。デモの Scene 6 は隣のページから履歴が漏れ込まないことに依存していますが、事前に転送先をクリアしているため、これを知る必要がありませんでした。
- **拡張パレット。** そもそも読み返せるのか、書き込みポートの自動加算がどこでも同じか。
- **R20 の残りのビット。** ここで扱っているのは bit0・bit4・bit5 だけです。デモが使うのがそれだけだからです。
- **コマンドごとの所要時間。** `CE` が測っているのは塗り潰し1つです。コマンド全体にわたる表があればはるかに多くを語りますが、機械間で比較するにはポーリング回数ではなくタイマーが必要になります。

## パッチではなく一覧から始める理由

本家 openMSX は実装を実機に対して評価します。量産品の存在しないチップでは、最初に欠けているのはコードではなく、実機が何をするのかという合意された答えです。複数の実装が記入した表があってはじめて、その議論が可能になります。そしてこれは、すべての実装を所有していなくても作れるものです。
